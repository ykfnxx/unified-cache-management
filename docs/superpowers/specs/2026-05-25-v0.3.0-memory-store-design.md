# v0.3.0 MemoryStore 设计

## 目标

在 `v0.3.0` 基线上新增 `MemoryStore`，同时满足三类约束：

1. 内部功能设计与 `develop` 分支当前 `MemoryStore` 保持一致。
2. 标准接口继续保留并兼容 `v0.3.0` 现有 `StoreV1` 使用方式。
3. 额外新增 per-token-per-layer 接口，并且接口挂在统一抽象层，而不是只挂在 `MemoryStore` 具体类型上。

这里的“功能设计一致”指的是：

- 本地数据模型仍然按 typed token chunk 管理，而不是按完整 shard buffer slot 管理。
- backend 交互仍然以完整 shard 为单位。
- 标准 `Lookup` 仍然只查本地 ready 状态，不主动向 backend 追查。
- `Load` / `Dump` 与 token-layer `LoadTokens` / `DumpTokens` 都走异步 task 模型。

## 非目标

- 不重构 `v0.3.0` 的 `CacheStore` 内部实现。
- 不把 `CacheStore` 和 `MemoryStore` 抽成新的共享缓冲层。
- 不在本轮把 `MemoryStore` 设计成 `develop` 那种 `Dictionary` 驱动配置入口；`v0.3.0` 继续使用强类型 `Config`。
- 不要求其他 store 真正实现 token-layer 接口；它们保持默认 unsupported 即可。

## 当前代码现实

### v0.3.0

- `StoreV1` 只有标准 `Lookup / LookupOnPrefix / Prefetch / Load / Dump / Check / Wait`。
- `Detail::TaskDesc` 只有标准 shard 描述，没有 token-layer 描述类型。
- `CacheStore` 的结构是：
  - `BufferManager`
  - `LoadQueue`
  - `DumpQueue`
  - `TransManager`
- `CacheStore` 使用强类型 `Config`，并通过 `detail/template/store_binder.h` 暴露 Python binding。
- Python 抽象 `ucm/store/ucmstore_v1.py` 也只有标准 block/shard 接口。

### develop

- `StoreV1` 已经补了默认 unsupported 的 `LookupTokens / LoadTokens / DumpTokens`。
- `Detail::types` 已经补了：
  - `TensorType`
  - `TokenLayerShard`
  - `TokenLayerTaskDesc`
- 当前 `MemoryStore` 的核心语义是：
  - 内部存储粒度是 `(block_id, layer_id, chunk_id, tensor_type)`
  - `LoadTokens` / `DumpTokens` 直接作用在 token-layer item 上
  - backend miss 统一退化成完整 shard load
  - backend dump 统一退化成完整 shard dump

## 推荐方案

采用“接口回挂统一抽象 + 内部实现按 MemoryStore 独立模型”的方案：

1. 在 `v0.3.0` 的统一抽象层补齐 token-layer 接口。
2. 在 `v0.3.0` 新增完整的 `MemoryStore` 模块。
3. `MemoryStore` 对外同时支持标准 shard 接口和 token-layer 接口。
4. 内部队列拆分、线程模型和构造方式尽量参照 `v0.3.0` `CacheStore`。

这样做的原因：

- 满足“标准接口也要有，per token per layer 接口也要有”。
- 不要求调用方拿到 `MemoryStore` 具体类型，统一抽象不被破坏。
- 其他现有 store 不会被迫实现新能力。
- `MemoryStore` 的内部模型可以保持和 `develop` 一致，而外部接线方式仍然适配 `v0.3.0`。

## 接口设计

### C++ 类型层

需要把 `develop` 中已经验证过的 token-layer描述类型回迁到 `v0.3.0`：

- 在 `ucm/store/detail/type/types.h` 新增：
  - `using TensorType = std::size_t`
  - `struct TokenLayerShard`
  - `struct TokenLayerTaskDesc : std::vector<TokenLayerShard>`

同时把 `TaskDesc` 和 `TokenLayerTaskDesc` 都补齐可选 `prerequisiteHandle` 字段，默认值为 `0`。

这样做的理由：

- token-layer dump 需要与上游 device stream/event 同步时，必须保留和 `develop` 一致的前置句柄能力。
- 该字段是纯增量字段，默认值为 `0`，不会破坏现有标准调用。

### C++ StoreV1

在 `ucm/store/ucmstore_v1.h` 上新增默认 unsupported 的三个接口：

- `LookupTokens(const Detail::TokenLayerTaskDesc&)`
- `LoadTokens(Detail::TokenLayerTaskDesc)`
- `DumpTokens(Detail::TokenLayerTaskDesc)`

这三个接口的默认实现都返回 `Status::Unsupported()`，只有 `MemoryStore` 真正实现它们。

这样做的结果：

- `CacheStore` / `PosixStore` / `FakeStore` / `Ds3fsStore` 都不需要新增真实逻辑。
- 统一抽象层保持一致，调用方可以通过 `StoreV1*` 访问 token-layer 能力。

### Python 抽象层

`v0.3.0` 的 Python 基类 `UcmKVStoreBaseV1` 也要同步扩展，否则 C++/Python 能力面会不一致。

Python 层新增 3 个默认 unsupported 方法：

- `lookup_tokens_on_layer(block_ids, layer_ids, token_offsets, tensor_types) -> List[bool]`
- `load_tokens_on_layer(block_ids, layer_ids, token_offsets, tensor_types, dst_addr) -> Task`
- `dump_tokens_on_layer(block_ids, layer_ids, token_offsets, tensor_types, src_addr, prerequisite_handle=0) -> Task`

这里故意采用 `*_on_layer` 命名，而不是新造一套名字，原因是 `develop` 的 pipeline connector 已经使用了这组命名，迁移成本最低。

Python 侧不新增 token-layer tensor-list 包装版本；本轮只提供 raw-address 版本，和 `develop` 的当前 connector 行为对齐。

### Python binder

`ucm/store/detail/template/store_binder.h` 需要扩展通用 binder 能力，新增：

- `LookupTokens(...)`
- `LoadTokens(...)`
- `DumpTokens(...)`

它们负责把：

- `ids`
- `layer_ids`
- `token_offsets`
- `tensor_types`
- `addrs`

组装成 `TokenLayerTaskDesc`，再转调到底层 `StoreV1`。

这样 `MemoryStore` 的 pybind 模块可以直接复用现有通用 binder 模板，而不需要单独写一套 token-layer C++ glue。

  - 对外实现 `StoreV1`

- `trans_buffer.*`

  - 复用 `TaskWrapper` 管理异步 task 生命周期
- `connector.py` / `memory_store.py.cc`
  - 暴露 Python 侧 connector 和 pybind 模块

## 配置设计

`MemoryStore` 在 `v0.3.0` 中继续使用强类型 `Config`，不走 `Dictionary` 驱动的 store 实现入口。

配置字段分两类：

### 与 v0.3.0 标准 store 对齐的字段

- `uintptr_t storeBackend`
- `std::string uniqueId`
- `int32_t deviceId`
- `size_t shardSize`
- `size_t blockSize`
- `size_t waitingQueueDepth`
- `size_t runningQueueDepth`
- `size_t timeoutMs`

### MemoryStore 专属字段

- `std::vector<size_t> tensorSizeList`
- `size_t memoryTokenChunkSize`
- `size_t memoryBufferCapacity`
- `std::vector<size_t> requiredTensorTypes`
- `std::unordered_map<size_t, std::vector<size_t>> tensorSizesByType`

本轮不把 `develop` 上的 `streamNumber / useGdr / cpuAffinityCores` 带回 `v0.3.0`。

原因：

- `v0.3.0` `CacheStore` 本身就是单 stream 模型。
- 这三个字段属于执行优化参数，不是 `MemoryStore` 语义成立的前提。
- 保持 `v0.3.0` 配置风格更重要，后续若有性能需要可以再增量补。

## 数据模型

`MemoryStore` 的内部状态继续使用 `develop` 当前模型：

- 本地最小存储单位是 token chunk：
  - key: `(block_id, layer_id, chunk_id, tensor_type)`
- 每个 chunk 保存：
  - payload bytes
  - token-ready bitmap
- 额外维护 `(block_id, layer_id)` 的 full-ready 集合。

full-ready 的定义保持不变：

- 某个 `(block_id, layer_id)` 下，所有 token offset、所有 required tensor type 都 ready，才算 full-ready。

完整 shard 的字节布局也保持和 `develop` 一致：

- 按 token 顺序遍历
- 每个 token 内再按 `requiredTensorTypes` 顺序拼接对应 payload

## 标准接口语义

### Lookup / LookupOnPrefix

- 只检查本地 `fullReady_` 状态。
- 不在标准 `Lookup` 中主动 fallback 到 backend。

这是有意保持与 `develop` 当前 `MemoryStore` 一致，即使它和 `v0.3.0` `CacheStore` 的 lookup 语义不同。

### Load

- 输入仍然是标准 `(block_id, shard_index, addrs)`。
- 先尝试从本地 chunk/full-ready 视图读完整 shard。
- 本地 miss 时，退化成完整 shard backend `Load`。
- backend 返回后先写回本地 chunk 状态，再执行 H2D 到调用方地址。

### Dump

- 输入仍然是标准 `(block_id, shard_index, addrs)`。
- 先从调用方地址做 D2H。
- 以完整 shard 视图更新本地 token chunk 状态。
- 再把完整 shard 提交给 backend `Dump`。

## Token-layer 接口语义

### LookupTokens

- 只检查本地 token-layer item 是否 ready。
- 不主动访问 backend。

### LoadTokens

- 输入项由 `(block_id, layer_id, token_offset, tensor_type, addrs)` 描述。
- 本地命中时，直接把对应 payload H2D 到调用方地址。
- 本地 miss 时，退化成所在 `(block_id, layer_id)` 的完整 shard backend `Load`。
- backend 数据先回填到本地 chunk，再抽出目标 item H2D 到调用方地址。

### DumpTokens

- 从调用方地址读取某个 token-layer item 的 payload。
- 更新本地 chunk ready 状态。
- 只有当某个 `(block_id, layer_id)` 已经 full-ready 时，才组装完整 shard 并提交 backend `Dump`。

这保证了 token-layer 增量写入不会向 backend 写半个 shard。

## 队列与线程模型

队列组织方式参照 `v0.3.0` `CacheStore`，但逻辑保留 `develop` `MemoryStore` 的语义。

### LoadQueue

拆成两阶段：

1. `dispatch`
   - 判断本地命中/缺失
   - 为缺失项提交 backend full-shard `Load`
   - 把待传输任务放入 running queue
2. `transfer`
   - 对 backend task 做 `Wait`
   - 必要时把 full shard 提交回本地 chunk 状态
   - 做 H2D

### DumpQueue

拆成两阶段：

1. `dispatch`
   - 可选 prerequisite wait
   - D2H
   - 更新本地 chunk/full-ready 状态
   - 必要时提交 backend `Dump`
2. `backend-wait`
   - 对已提交的 backend task 做 `Wait`

这里明确不再引入额外“隐藏的 backend-host 第三阶段”，因为 `develop` 当前 MemoryStore 也已经把 dump 收敛成 queue-visible backend submit/wait 结构。

## 与 CacheStore 的关系

需要复用的是模式，不是数据结构。

明确复用的点：

- 强类型 `Config`
- `TransManager + LoadQueue + DumpQueue + TaskWrapper` 组织方式
- `StoreBinder` / connector / pybind 模块组织方式
- 异步 task 生命周期管理方式

明确不复用的点：

- `CacheStore::TransBuffer` 的完整 shard buffer slot 模型
- `CacheStore::BufferManager` 的本地命中结构
- `CacheStore` 的 lookup-through-backend 语义

## 测试设计

新增 `ucm/store/test/case/memory/`，至少覆盖以下行为：

1. `StoreV1` 默认 token-layer 方法返回 unsupported。
2. `MemoryStore` token-layer dump/load round-trip 正确。
3. `MemoryStore` token-layer lookup 只查本地状态。
4. `LoadQueue` backend miss 仍然是 queue-managed async load。
5. `DumpQueue` backend dump submit 不会被前一个 backend wait 阻塞。
6. token-layer dump 只有在某个 layer full-ready 后才触发 backend full-shard dump。
7. 标准 `Dump` -> 标准 `Load` 仍能完成 full-shard round-trip。

测试风格参照 `v0.3.0` 现有：

- `cache_load_queue_test.cc`
- `cache_dump_queue_test.cc`
- `cache_trans_manager_test.cc`

## 兼容性约束

这次改动必须保持以下兼容性：

- 现有 store 的标准接口不改语义。
- 其他 store 不需要新增 token-layer 真实实现。
- Python 现有 connector 不因为新增 token-layer 方法而变成抽象类无法实例化。

因此：

- C++ `StoreV1` 新接口必须提供默认 unsupported 实现。
- Python `UcmKVStoreBaseV1` 新接口必须提供默认 `NotImplementedError`，不能标成新的 `@abstractmethod`。

## 实施顺序

建议后续实现按这个顺序进行：

1. 先扩 `types`、`StoreV1`、Python base、`StoreBinder`。
2. 再新增 `MemoryStore` 基础骨架、`Config` 和构建接线。
3. 先写标准 full-shard 路径测试与实现。
4. 再写 token-layer 类型、binder、connector 测试与实现。
5. 最后补 queue 结构测试与 async 行为对齐。

## 验收标准

实现完成后，需要同时满足：

- `v0.3.0` 所有现有 `CacheStore` 相关测试继续通过。
- 新增 `MemoryStore` 单测通过。
- `MemoryStore` 的标准接口可用。
- `MemoryStore` 的 per-token-per-layer 接口可用。
- 标准接口与 token-layer 接口共享同一套本地状态，不出现两套缓存视图不一致。
